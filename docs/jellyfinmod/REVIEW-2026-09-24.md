## S4-R4 — No `interface_patched` / `interface_restored` history rows

- **Status:** **fixed and verified** 2026-09-24, plugin `61e2003`. **Priority:** P2. The engine reports every patch and restore to `TakeoverHistory`, which writes the row through a scoped context (ids, both hashes, `patchedBy` / `restoredBy`, never a path); the database initializer now starts before the bundle installer. `patchedBy` is `automatic` / `setting` / `bundle` only. **Evidence:** `PhaseSevenTakeoverIntegration` asserts exactly one row each for a fresh install (`automatic`), a restart with nothing to change (none), takeover off (`interface_restored`, `setting`), takeover on (`setting`), a bundle change (`bundle`, both ids) and Restore stock now (`restoreStock`), in a real migrated SQLite database, none carrying a path; live on 28096 each deploy wrote one `interface_patched` row with `patchedBy: bundle`, and a base-URL re-render one with `automatic`.
- **Location:** plugin, `JellyfinMod/Services/Web/WebRootTakeover.cs:194–262` (`Patch`) and
  `:264–293` (`Restore`); nothing in `JellyfinMod/` references either event type.
- **Trigger:** any patch or restore, including the automatic one at first start (decision 7).
- **Cause:** §4.6 makes the history row a requirement ("must never be silent … writes an
  `interface_patched` / `interface_restored` history row"), the data-model table lists both
  events, and S7's task text says "add … the history events". The engine writes a log line and
  updates `state.json`; it has no database access and never adds a `HistoryRecord`. The S5
  evidence found the table empty after several patches and restores and recorded it as "found,
  not fixed (S4 scope)"; PHASE7's handover still lists S7 as done.
- **Impact:** the one durable, Dashboard-visible answer to "why did `/web` change?" is missing.
  Health and the Interface section show only the current state; a patch that was later restored
  leaves no record. Also, `PatchedBy` (`:296`) emits `startup` and `restore requested` besides the
  documented `automatic` / `setting` / `bundle`; the web shows anything but `setting` as "the
  plugin itself", so nothing breaks, but §4.6 and the API contract name three values.
- **Fix direction:** have `WebBundleInstaller` and `InterfaceSettingsController` write the row
  through a scoped `ModDbContext` after `ReconcileAsync` returns a changed state (bundle id, both
  hashes, `patchedBy`; never a path), or give the engine a callback. Align the `patchedBy`
  vocabulary with the contract or update the contract.
- **Acceptance:** on the isolated instance, a fresh install, a takeover-off, a takeover-on and a
  bundle change each leave exactly one row with the expected type and fields; the S4 integration
  runner asserts it.

## S7-R1 — The XML import mutates the live configuration before the database write succeeds

- **Status:** **fixed and verified** 2026-09-24, plugin `732cea3`. **Priority:** P2. The import reads the XML into locals, saves the row, then clears and saves the XML (restoring the live fields if that save fails) and removes secrets last; the catch logs what is true. **Evidence:** `PhaseSevenSettingsIntegration` provokes a real SQLite error on the real file during the settings save (a trigger aborting the update): the in-memory configuration, the XML file (byte-identical) and the secret store are unchanged, discovery still reports the token and TMDB receives it, seed protection still reads the XML endpoint and reaches Transmission. A real filesystem failure during the XML save (its path is a directory) leaves the row holding the values, the live fields put back and no secret removed; the next start imports cleanly. The same test fails against the previous code ("after a failed database save the in-memory configuration still holds…").
- **Location:** plugin, `JellyfinMod/Services/Settings/SettingsStore.cs:56–109` (`RunAsync`:
  the XML fields are emptied at `:63` and `:97–99`, the database is saved at `:106`);
  `JellyfinMod/Data/DatabaseInitializer.cs:60–76` (`ImportXmlSettingsAsync`, log text at `:73`).
- **Trigger:** `SaveChangesAsync` fails during the startup import (locked or full disk, an
  I/O error) on an install that still holds the TMDB token reference or the seed-protection
  connection in the XML — that is, every pre-S7 install, once.
- **Cause:** `xml` is `Plugin.Instance.Configuration`, the live object. `RunAsync` nulls
  `TmdbReadAccessTokenRef` and empties the Transmission fields on it *before* saving the settings
  row. When the save throws, the caller logs "they stay where they are" and does not save the
  XML — but the in-memory configuration has already lost the values. `TmdbClient`, the seed
  reader and `DiscoveryDtoAsync` read that in-memory object first and fall through to a settings
  row that never received the reference, so discovery reports `not_configured` and seed
  protection `transmission_unconfigured` immediately. The next `SaveConfiguration()` from any
  path (the Interface switch, `PATCH /Settings/Retention`, the host's plugin-configuration API)
  persists the emptied object, and the reference is gone from both stores while the secret stays
  orphaned in the `0600` file.
- **Impact:** a one-time import step that, on failure, silently loses the configured TMDB token
  and seed-protection connection instead of leaving them where they were; retention is blocked
  (fail-safe) and discovery is off until an administrator re-enters both. The log message is
  wrong about what happened.
- **Fix direction:** read the XML values into locals, save the database, and only then clear the
  XML fields and remove obsolete references; or work on a copy and apply it after the save.
  Make the catch's message true.
- **Acceptance:** the S7 suite runs the import against a read-only or locked database and shows
  the XML fields, the in-memory configuration and the secret store unchanged, discovery still
  working from the XML reference, and a clean import on the next start.

## S7-R2 — A re-run of the import can delete a secret the settings row still references

- **Status:** **fixed and verified** 2026-09-24, plugin `732cea3`. **Priority:** P3. A reference is removed only when neither the row, the XML, a client, an indexer nor a Prowlarr source holds it, and an unchanged re-run advances no revision. **Evidence:** the S7 suite re-runs the import with the same token and password references in the XML and the row: both secrets survive, no revision moves, the XML is emptied in memory and on disk, seed protection and discovery Tests pass.
- **Location:** plugin, `JellyfinMod/Services/Settings/SettingsStore.cs:77` and `:91–94`,
  `:106–109`.
- **Trigger:** a previous import saved the database but its XML save failed or was overwritten
  by a concurrent host-API `POST /Plugins/{id}/Configuration` carrying the old fields, so the
  XML still names the same Transmission password reference the settings row now holds.
- **Cause:** `obsolete.Add(settings.SeedProtectionPasswordRef)` runs unconditionally; in the
  `separate` branch the row is then set to the XML reference, which is the same string, and the
  loop removes it from the store.
- **Impact:** seed protection's password disappears while its reference remains; the next seed
  check fails as unavailable and reclamation is blocked until the password is re-entered.
- **Fix direction:** add a reference to `obsolete` only when it differs from the value being
  written (as the TMDB branch at `:59` already does).
- **Acceptance:** the suite re-runs the import with the same reference in both places and the
  secret survives.

## S7-R3 — An imported RPC URL is not validated and is echoed with credentials

- **Status:** **fixed and verified** 2026-09-24, plugin `732cea3`. **Priority:** P3. The imported address is stored without user information (and without query or fragment); a user name from it fills an empty username, a password becomes a store secret only when none was referenced; the cleaning is logged without the URL. `SeedProtection` also never echoes an address with user information. **Evidence:** the S7 suite imports `http://user:password@host:port/transmission/rpc`: the row, `rpcUrl` and `effectiveRpcUrl` carry no credentials, the password is in the store, the Test reaches Transmission; every response and log line is leak-checked.

- **Trigger:** an operator once typed `http://user:pass@host:9091/transmission/rpc` into the old
  seed-protection field. The typed `PATCH` refuses userinfo (`ValidEndpoint`), the import does not.

## S4-R5 — The takeover reads the base URL once, at process start

- **Status:** **disputed, with live evidence**, 2026-09-24. **Priority:** P3. On Jellyfin 12.0.0 (28096) a base URL saved through `/System/Configuration/network` without a restart did not move routing: every request, `/web/` and `/JellyfinMod/Health` included, was redirected to `/jfprobe/…`, which answered `404` until the restart — the host needs a restart for a base URL change whatever the plugin does, so re-rendering on the configuration event would change nothing a user can load. After the restart the engine re-rendered under `/jfprobe/web-mod/<id>/` (Health `patched`, an `automatic` history row), and again when the prefix was put back. Reading the prefix once per process therefore matches what the host serves; no code change. §4.6 now says so.
  was not exercised.
- **Location:** plugin, `JellyfinMod/PluginServiceRegistrator.cs:72` (read at DI construction);
  `JellyfinMod/Services/Web/WebRootTakeover.cs:55` (stored in a readonly field), `:153`
  (compared against the record).
- **Trigger:** an administrator changes Networking → Base URL while the server runs.
- **Cause:** Jellyfin applies the prefix to routing at once; the patched `index.html` still roots
  its assets at the old prefix, so every script and stylesheet fails and the failsafe loads the
  stock copy. Reconcile can only notice a change against the record, and `_baseUrl` does not
  change until a restart. REVIEW-2026-09-23 records the fix as "re-renders when it changes",
  which is true only across restarts.
- **Impact:** `/web` reverts to stock until the next server restart, with Health still reporting
  `patched`. No data risk.
- **Fix direction:** read `IServerConfigurationManager.GetNetworkConfiguration().BaseUrl` at
  every reconcile, and reconcile on the host's configuration-updated event.
- **Acceptance:** on the isolated instance, changing the base URL without a restart yields a
  re-rendered page under the new prefix and a Health state that matches what `/web` serves.

## S9-R3 — Changing the source's address leaves synced feeds on the old host until the next sync

- **Status:** **fixed and verified** 2026-09-24, plugin `11c457f`. **Priority:** P3. ## S5-R1 — The entrypoint replaces `system.xml` without checking that the rewrite completed

- **Status:** **fixed and verified** 2026-09-24, plugin `43bc27c`. **Priority:** P3. `system.xml` is replaced only when awk succeeded, the output is the input plus the entry's lines and ends with the closing element; the original is kept for one start. **Evidence:** `tests/image/entrypoint-rewrite.sh` on the test host in disposable containers of `capische/jellyfinmod:0.1.0.0`: a normal volume registers and keeps every line; a tmpfs filled until 16 KiB are free for a 48 KiB file leaves `system.xml` byte-identical and logs the refusal; a read-only config directory likewise; the next start removes the backup. The previous entrypoint moved the truncated file over `system.xml` in the same full-volume case.
- **Location:** plugin, `docker/jellyfinmod-entrypoint.sh:158–176` (`register_repository`:
  three `awk` variants write `$system.jellyfinmod`, then `[ -s ]` and a `grep` for the entry gate
  the `mv`).
- **Trigger:** the config volume fills, or `awk` fails, after the entry line was written but
  before the rest of `system.xml` was copied — a first start on a nearly full volume.
- **Cause:** `awk`'s exit status is ignored and the gate accepts any non-empty file that contains
  the entry; a truncated file passes.
- **Impact:** a truncated `system.xml` is moved over the real one. Jellyfin then fails to parse
  its server configuration and regenerates defaults, losing the operator's server settings (the
  plugin's own data is untouched). Rare, and only once per volume, but the file is the one the
  script has no business breaking.
- **Fix direction:** check `awk`'s exit status, compare line counts (output = input + the entry's
  lines), and `mv` only then; keep a `.bak` beside it for one start.
- **Acceptance:** an image test that makes the volume read-only or full during the rewrite
  leaves `system.xml` byte-identical and logs the refusal.
