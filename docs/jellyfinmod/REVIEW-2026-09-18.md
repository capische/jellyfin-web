## 2. Executive summary

**Verdict.** Phases 1–3 are implemented and mostly coherent. Phase 1 and Phase 2 behaviour holds
up at the scale of the test library. The Phase 3 retention engine is carefully fenced, with
exact-path checks, a policy-version re-check, hardlink and seed checks and a durable operation
record, but it is **not yet safe to enable on media that matters**. The review found one critical
and several high defects in how the engine decides *when* a title is due and how it recovers.
Its only enabled deletion path has also never run on the live host. Phase 4 should not start
building on this line until the blockers in §7 pass.

The most important risks (single-source items marked):

1. **Re-acquired media is deleted almost at once** (plugin-retention-policy#1, critical).
   Reclaiming or unbinding a title leaves its old evaluation and observations in place. When the
   file comes back (a manual copy, or Phase 4 "Get again"), the old past deadline is reused and
   the next daily run unlinks the restored file. plugin-retention-policy#2 (high) is the same
   class of bug: a new target's grace can start at `EnabledAt` rather than now. Fix: T7.
2. **The last check before an unlink uses stored watch data, not live data**
   (critic-invariants#1, high). A dropped favourite or "mark unwatched" event can let a
   protected title be deleted. prior-H1 (high) is the opposite failure: Any and Selected modes
   stall until someone runs a repair task by hand. **Order matters:** fixing prior-H1 by
   reading live data *before* the T7 grace floor would make the critical bug the normal path.
   Fixes: T7, then T8.
3. **Crash recovery after an unlink is dead code in production** (plugin-retention-safety#1,
   high). The runner never calls `RecoverAsync`, so an interrupted unlink leaves the entry
   `onDisk`, writes `media_missing` rather than `reclaimed`, and keeps the operation open for
   good. Fix: T9.
4. **Enabled retention has never run on the live host** (plan-ops#1, high). The T6 countdown,
   due-filter and reclaimed-UI evidence used hand-seeded database state, and every automated
   suite stubs Jellyfin's host services and authorization (tests-contract#2). Fix: T18, which
   re-runs Phase 3 acceptance on disposable media.
5. **Catalog operations can erase retention intent.** Refresh hard-deletes episodes missing from
   TMDB and cascades away their bindings, evaluations and operations (plugin-authz-entries#1).
   Refresh also bypasses locks (prior-H2). Remove cascades operations (prior-M1) and drops Keep,
   so reconciliation recreates the entry unprotected (plugin-reconciliation-data#1). Part of
   the fix exists only on `jellyfinmod-phase1` (`fba11e3`). Fixes: P7 and T10.
6. **The primary TV surface has functional regressions.** Legacy/TV filters break combined
   browse (web-library-search-details#1). TMDB "Add" results beyond the first screen cannot be
   reached (web-library-search-details#2). Merged Home rows do not refresh after playback
   (web-home-rules-tv#1). The legacy grid needs `display: contents`, which older webOS (Chromium below 65) lacks
   (critic-gaps#3, conditional). Fixes: W8–W11.
7. **Process and deployment gaps.** Fixes land on the oldest branch and never reach the
   integration line (plan-ops#3, single-source). Production master fixes are missing from every phase branch
   (plan-ops#4, single-source). `jellyfin-sync` defaults to production (plan-ops#2). Deployed builds cannot be
   identified (plan-ops#5, single-source). Fixes: X1, X3 and X4.

**Proposed safety gate (review 2026-09-18, not user-approved):** Phase 3 is implemented.
Automatic retention stays disabled on non-disposable media until the review blockers T7, T8, T9,
T10 and T18 pass on the isolated test instance; Selected user mode on real media also waits for
T13. This defers enabling retention; it does not change the accepted automatic-expiry decision.

### 4.5 Critical and high details

**plugin-retention-policy#1 — re-acquired media is due immediately (critical).** Reclaim removes
the binding and marks the target `reclaimed`, but nothing resets its `RetentionEvaluation` or
`CompletionObservation` rows. When the title is bound again, the evaluator reuses the old
`priorDeadline`, and never moves a deadline earlier. *Scenario:* movie M is completed on
Jan 1 and reclaimed on Jan 15. On Mar 1 the admin copies it back, or Phase 4 "Get again" grabs
it. At the next daily run the deadline is still Jan 15, so the restored file is unlinked before
anyone watches it. This repeats on every re-acquisition. Verifiers found the mechanism stronger
than reported: nothing refreshes observations on rebind, so no Jellyfin user-data reattach is
needed. Reclaimed episodes also keep past-deadline rows, so the series appears under "Due within
7 days" indefinitely. *Fix (T7):* in the same transaction as reclaim or unbind, reset the
evaluation, mark observations stale and record a representation baseline. Ignore observations
for item IDs that are no longer bound. Exclude unbound targets from the due filter and series
summaries.

**plugin-retention-policy#2 — grace starts at `EnabledAt` (high).** A brand-new evaluation row
matches none of the conditions that move eligibility to now. A native `LastPlayedDate` from
years ago therefore yields a deadline that is already past. *Scenario:* an admin runs the
evidence repair task proactively, right after a title is re-cataloged. The first evaluation sees
complete evidence and the title is due at the next run. One verifier lens argued for medium,
because the path needs the repair task, or a single-user library, to run before any other full
evaluation. The majority kept high because the planned prior-H1 fix would make this path
normal. *Fix (T7):* floor eligibility at the time the current representation was first bound,
and at least add `!hadPriorEvaluation`. Land it before T8.

**plugin-retention-safety#1 — recovery after unlink is unreachable (high).** The runner
recovers open operations through `ReclaimAsync`. That method returns `NotStarted` unless a fresh
preview is `Due`, and an operation whose file is already unlinked is never `Due`. The
recovery branches are reached only by tests that call `RecoverAsync` directly. *Scenario:* the
task is cancelled or the container stops after the unlink but before the completion write. The
entry stays `onDisk`, the next scan writes `media_missing` instead of `reclaimed`, and the
operation stays open for good. Stuck operations inflate `Interrupted`, and after 25 of them
reclamation would stop, which verifiers call theoretical. No media beyond the intended file is
lost. One verifier lens argued for medium on that basis. *Fix (T9):* run recovery at run start
under the gate, look up open operations before the Due gate, and persist terminal states.
Count only resolved actions.

**critic-invariants#1 — stale watch data at the final gate (high, plausible).** PHASE3 T3
requires protection checks "immediately before each deletion". In fact the executor's last gate
re-evaluates persisted observations, and nothing re-reads live favourite, resume or played state
from Jellyfin. The listener queue drops work on shutdown, on processing errors, and for items
unbound at event time. The repair task has no trigger. *Scenario:* a user favourites, or marks
unwatched, a scheduled movie while `jellyfinmod-test` restarts or the item is being rebound. The
event is lost and the 03:00 run deletes the file. *Fix (T8):* read live user data for every
accessible user across all versions inside the lease. Block with a stable
`live_user_state_changed` reason. Retry failed listener work.

**prior-H1 — Any and Selected modes stall (high).** A target is blocked with
`completion_evidence_missing` whenever *any* accessible user lacks an observation. Observations
come only from that user's own events or from the trigger-less repair task. Verifiers widened
the scope: a new user or an access grant flips already-scheduled targets to blocked and
discards their deadline. *Fix (T8):* read or seed live user data when an observation is missing
(only after T7). Give repair a default trigger. Add a regression where a second user never
touches the movie.

**plan-ops#1 — no live enabled run (high).** The enabled chain has no live evidence: real
completion events, then evaluation, then the scheduled runner, then the executor, with real
Transmission paths. The T6 countdown, due-filter and reclaimed-UI checks used reversible
hand-seeded rows, and the T6 runner takes expected states from environment variables. Verifiers
narrowed the claim. T3 did unlink one real file live. Physical webOS was not a Phase 3 rule.
*Fix (T18):* an enabled cycle on disposable fixtures in Any and Selected modes, with no database
edits, followed by the browser runner against the resulting real state.

**plugin-reconciliation-data#2 — absence detection switched off per library (high).** Absence
confirmation returns early if *any* absent binding fails its storage-identity check. Any
conflict or failed title marks the library incomplete, and one unnumbered native episode makes
the whole series fail. *Scenario:* one date-named episode is in the TV library, then a user
deletes 30 watched episodes by hand. They stay `onDisk` with no missing event. Verifiers
corrected "indefinitely" to "until an undiscoverable, lossy manual Remove". *Fix (R6):* scope
incompleteness to the affected title, check existence directly for null or out-of-location
identities, and diagnose unnumbered episodes one at a time.

**plugin-reconciliation-data#3 — library re-create or rename (high, plausible).** Native item IDs
survive a library re-add under a new name, but the library ID changes. Every title then
conflicts, and the old entries point at a dead `TargetLibraryId`, which hides them from everyone.
Admin DELETE also returns 404, so recovery needs a database edit. No media is lost, because
retention blocks orphaned targets. *Fix (R7):* first check on the isolated test instance whether
a rename changes the library ItemId. Then re-home entries with a `library_moved` event, define
overlapping libraries, and list orphaned entries in diagnostics.

**prior-H5a — access-check fan-out (high, fixed on phase1 only — carry forward).** `CanRead`
lists the library once per bound entry, and `CanReadEpisode` scans series per episode. With
about 160 entries, one Browse or Discover request makes about 160 recursive library queries per
media type. Pi latency was never measured. `fba11e3` batches the checks, but its `BuildDetail`
hunk conflicts with Phase 3's retention additions. *Fix (P7):* port and adapt it, then record
p50/p95 before and after.

**web-library-search-details#1 — TV filters break combined browse (high).** The TV layout runs
the legacy controllers, whose filter dialog writes pipe- or comma-joined strings and a
`Filters` token list. `toRequest` passes the strings through, so the plugin's array binding
returns 400 and the client silently falls back to native. Every file-less and reclaimed card
disappears, and a reset makes this permanent for that device. Status, feature, resolution and
Favorites filters are silently ignored. The legacy dialog also has no File or Due filters. *Fix
(W8):* normalize the legacy query and map `Filters` and the feature flags. Add File and Due to
the TV dialog. Log non-404 failures.

**web-library-search-details#2 — unreachable discovery cards (high).** `.jfmod-discoveryCards` is
`display:flex; overflow:hidden`, with fixed-width, non-wrapping items. Touch and mouse users see
only the first screen. For a query with more than about 10 movie matches, no series suggestion
is reachable at all. On TV (Chromium 64 and later), D-pad focus lands on clipped cards.
Desktop keyboard Tab still works. *Fix (W9):* use the `emby-scroller` + `scrollSlider` markup
already used by `EntrySection`, and assert viewport visibility in the browser runner.

**web-home-rules-tv#1 — Home rows go stale (high).** The merged rows read the `ResumeItems`,
`NextUp` and `LatestMedia` query keys, but the mod invalidates only `['User', id, 'Items']` and
its own keys. Replacing the upstream loaders also dropped their `data-monitor` refresh.
*Scenario:* on TV, a user plays S01E03 from Continue watching and presses Back. The row is
unchanged, and E04 does not appear. A wanted title vanishes from Recently Added when its file
arrives. Verifiers noted this affects every layout that renders the legacy Home, and that the
production fix `b72ac53721` touches the same handler. *Fix (W10, after X1):* invalidate those
keys on playback stop, on a zero-crossing of played state and on LibraryChanged. Move the logic
into a feature hook.

**critic-gaps#3 — `display: contents` on old webOS (high, conditional).** The legacy/TV grid
mounts cards into a wrapper made transparent with `display: contents`, which Chromium supports
from version 65. On webOS 3.x/4.x the combined Movies and Shows grids collapse into one column.
Verifiers dropped the `inset` sub-claim, because postcss already expands it. Severity stays high
only if the household TV runs Chromium below 65. Otherwise only a low `:focus-visible` note
remains. *Fix (W11):* give the wrapper the container's layout classes, or mount into the
container. Record `navigator.userAgent` from the TV as physical evidence.

## 8. Ideas and recommendations beyond defects

Each idea below comes from the verifiers' fix notes, not from new scope:

- **Give retention one "representation baseline".** A per-target `RepresentationBoundAt`
  (T7) closes plugin-retention-policy#1 and #2 together and gives Phase 4 "Get again" a clear
  contract. Observations older than the baseline never count.
- **Aggregate observations per target, not per item.** Resume or favourite on any version
  protects; completion needs no resumable version (T8). The same aggregate serves the listener,
  the repair task and the live pre-unlink read.
- **Expose server capabilities, not version guesses.** Health `revision`, `lastMigration` and
  `capabilities` (X4) would let the web hide unsupported filters (W14), let Phase 4 A7 gate
  controls, and let deploy evidence tie a DLL to a commit. The migration guard stops an older
  build from running on a newer schema.
- **Use a public retention vocabulary for non-admins.** Map reasons to `protected`, `waiting`
  or `scheduled` with no per-user detail, and keep full reasons on admin-only endpoints (T15).
  This keeps the countdown useful without exposing household activity.
- **Scope failure to the smallest unit.** Per-title absence (R6), per-episode conflicts (R9) and
  per-candidate discovery failures (P8) share one pattern: one bad item should produce a
  diagnostic, not disable a library, a series or a page.
- **Prefer stable storage identity.** Mount point, fstype, root and filesystem UUID or `f_fsid`,
  plus a re-baseline pass before absence confirmation and preview, would end the reboot stall
  (prior-M7, R6).
- **Give distinct reasons for fail-closed cases.** For example, "Transmission index incomplete
  (N files)" instead of a generic `seed_state_unknown` (T17), `multi_part_unsupported` (T16) and
  `media_not_writable` (T9). Admins can then act on a blocked preview.
- **Keep mod logic behind one-line mounts.** Moving websocket invalidation and Home composition
  into feature hooks (W10) makes the production-master merge (X1) and later upstream rebases
  semantic in one place rather than across upstream files.
- **Keep boundary servers as the test backbone.** The TMDB, Transmission and planned Torznab HTTP
  fixtures are real boundaries, and they can count upstream calls (P8, W13). Pair them with
  real-host runs on the isolated test instance (X5) rather than extending host-service stubs.
- **Report space honestly for hardlinked media.** Until Phase 5 removes seeding copies, show
  "library link removed; seeding copy remains" when physical bytes are 0, and credit space
  freed later to the original reclaim (prior-H3 residual).
