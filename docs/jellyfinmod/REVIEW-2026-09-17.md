## 2. Executive summary

The architecture is sound and the discipline is unusually high: server-side authorization,
durable intent before unlinking, inode/mount checks, fail-closed seed checks, and real-host
acceptance evidence. The main risks are not in the basic design. They are:

1. **Retention stalls in Any user / Selected user mode.** New media never gets scheduled without
   a manual repair run, because a missing per-user observation blocks evaluation and nothing
   creates observations automatically (H1).
2. **A metadata Refresh undoes Phase 2/3 state.** It can turn a `reclaimed` entry into
   `none`/`onDisk` and bypasses bindings, locks and the retention gate (H2).
3. **The planned pipeline never frees disk space.** Phase 5 imports with hardlinks, and Phase 3
   correctly counts a hardlinked unlink as 0 bytes freed. No phase removes the seeding copy (H3).
4. **The seed-protection rules are weaker than the README promises, and the phases disagree on
   the download client.** The idle limit is treated as a met seed goal. There is no minimum
   seed time. Phase 3 reads Transmission, but Phase 4 plans only a qBittorrent driver (H4).
5. **Pi performance was never measured**, even though PHASE1 §4 required it. Access checks list
   the whole library once per entry and once per episode. Every Movies/TV page load waits on the
   combined browse even when it is unused. A retention batch runs about 76 full previews (H5, H6).

By its own gates, **Phase 3 is not complete yet**: T5 has just been committed without acceptance,
and T6 has not started. The live acceptance items in `REVIEW.md` and physical webOS checks remain
open (§5.2).

## 3. Code findings

### 3.1 High

#### H1 — Any user / Selected user retention needs a manual repair run to schedule anything · Confirmed

- `RetentionEvaluator.cs:156` blocks with `completion_evidence_missing` when **any**
  accessible user has no `CompletionObservation`, whatever the watched-user mode.
- Observations are created only by `RetentionCompletionService.RefreshAsync`. That runs from
  `UserDataSaved` for the user who touched the item, and from `RefreshAllAsync` in the repair task.
- `RetentionEvidenceRepairTask.cs:31` has **no default triggers**. No handler for user creation
  or new bindings seeds observations.

**Scenario:** Any user mode with four users. A new movie is scanned and bound, and `oleksii`
watches it, so only `oleksii` gets an observation. The other three have none, so the movie stays
`blocked / completion_evidence_missing` indefinitely. The T5 UI shows "Automatic removal is
blocked." The T1 Pi acceptance ran the repair task first (224 observations), which hid this.

**Fix:** in the evaluator, when an observation is missing, read live `IUserDataManager` state
instead of blocking. Only block when the item or user cannot be resolved. Also give the repair
task a default weekly trigger, and seed observations when reconciliation creates a binding or a
user is created.

#### H2 — `POST /Entries/{id}/Refresh` bypasses reconciliation and can erase `reclaimed` · Confirmed

`EntriesController.cs` Refresh:

- `:155` clears every kept episode's `JellyfinItemId`. `:174` sets
  `entry.State = owned is null ? None : OnDisk`, so a **reclaimed movie becomes `none`** and
  loses its provenance.
- It sets `entry.JellyfinItemId` from `LibraryAccess.FindOwned`, using the admin's own
  visibility and `FirstOrDefault`. It never touches `EntryBindings`/`EpisodeBindings`, so
  `Entry.JellyfinItemId` and the binding tables can disagree afterwards.
- It holds neither `ReconciliationLibraryLock` nor `RetentionExecutionGate`, so it can race a
  reclaim that is completing or a scan.

**Fix:** have Refresh update metadata and episode identity only. Re-derive availability by
calling the Phase 2 reconciliation service under the library lock. Never assign `State`
directly. Add a regression case (reclaimed entry → Refresh → still `reclaimed`, bindings intact)
to the Phase 3 integration suite.

#### H3 — With hardlinked imports, retention frees 0 bytes by design · Confirmed (design gap)

`RetentionExecutor.cs:215` records `PhysicalBytesReleased = 0` when the link count was above 1.
That is correct. However, README §6 and Phase 5 require hardlink imports, so every imported file
has link count ≥ 2 while its download copy exists. Retention will unlink the library copy, free
nothing, and report the title `reclaimed`. Phase 3 T3 forbids torrent/data removal, and PHASE4
says "No acquisition operation … removes a torrent". **No phase owns removing the seeding copy
once seed goals are met.** Feature 3 ("reclaim the disk") therefore never happens for media
acquired through the planned pipeline.

**Fix (plan):** add an explicit task, in Phase 5 or a Phase 3.5, to remove the torrent and its
data from the client after the retention unlink and after seed goals are met. Use the same
durable-operation pattern. Until then, the run summary and UI should say "unlinked, still seeding
copy" rather than implying disk was reclaimed.

#### H4 — Seed protection is weaker than specified, and the client plan is inconsistent · Confirmed / Plausible

`TransmissionSeedClient.cs`:

- `:186` `idleSatisfied = idleGoal.HasValue && etaIdle == 0`, and `:192` ORs it into
  `SeedGoalSatisfied`. Transmission's idle limit means "stop after N idle minutes". It is **not a
  minimum seeding time**. On a quiet private-tracker torrent the file becomes deletable soon after
  it goes idle, breaking hit-and-run rules. README §6 promises "never delete a file the torrent
  client is still seeding under its ratio/time goal". Transmission has no native minimum seed
  time, so the plugin needs its own floor. *(Confirmed)*
- `:74–77`: any torrent file that cannot be `statx`-ed from inside the **Jellyfin** container
  sets `CompleteFileIndex = false`. That blocks **every non-torrent candidate**. Transmission
  usually runs in another container with different mount paths, and there is no path-mapping
  setting like Sonarr's "Remote Path Mappings". One stale torrent with deleted data has the same
  effect. The failure is safe, but it can quietly disable retention. *(Plausible; check the Pi's
  compose mounts.)*
- Phase 3 built a **Transmission** read adapter from the installed client, but PHASE4 makes
  **qBittorrent** "the first and only write driver". Torrents added by Phase 4 would be invisible
  to Phase 3's seed protection unless a qBittorrent read adapter is built too.

**Fix:** add a plugin-side minimum seed ratio and seed time, per indexer later, as a hard floor
in addition to client goals. Add path mappings, or scope the index to torrents under configured
download roots so unrelated stale torrents don't block everything. Settle on one client before
starting Phase 4 (§5.3).

#### H5 — Access checks list the whole library once per entry, and once per series per episode · Confirmed

- `LibraryAccess.cs:48`: `CanRead` for a bound entry calls `GetNativeItems(user, type, library)`,
  a recursive library query, **per entry**, and nothing caches it.
- `LibraryAccess.cs:126`: `CanReadEpisode` lists **all series, then all episodes of each**, per
  episode.
- It is called in loops: `EntriesController.cs:43` (List), `BrowseController.cs:45`,
  `DiscoverController.cs:28`, and per episode in `BuildDetail`.

With the current 163 entries, one Browse or Discover request runs about 160 full library
queries. A 60-episode series detail runs about 60 × (series query + one episode query per
series). The cost grows as entries × library size, and on a Pi it will dominate latency.

This multiplies because:

- `useLibrary` always runs `useBrowse`, and `ItemsView` shows `<Loading/>` while
  `isSelectingSource`. **Stock Movies/TV pages wait for the combined browse even when there are
  no catalog entries** and the native result is used.
- Search sends 2 × Browse (`limit: 200`) and 2 × Discover per query. Each Discover page makes up
  to 20 uncached TMDB detail calls (`DiscoverController.cs:43`).
- `BrowseController.cs:52/80` also loads user data for every native item on every page request.

PHASE1 §4 said to "measure latency and memory on the Pi before accepting this approach". No
measurement is recorded in any phase document.

**Fix:** per request, compute the accessible native ID set once per (user, library) and check
membership. Load episode visibility once per series. Skip the Browse call when the client already
knows `hasCatalogEntries` is false and no File filter is active, or cache that flag. Add a
TMDB response cache table with a TTL. Record p50/p95 latency on the Pi for Browse, Discover and
Detail with a synthetic large library (for example 5k movies / 50k episodes on the test instance).

#### H6 — Each retention action recomputes everything up to 3 times · Confirmed

- `RetentionExecutor.cs:29, :52, :169`: each `ReclaimAsync` calls `PreviewAsync` up to three
  times, and `RetentionRunner.cs:85` adds one per batch. That is about 76 previews for a
  25-path batch.
- Each preview runs `EvaluateAllAsync` (per target: several queries plus a `SaveChanges`,
  **always writing `EvaluatedAt`**) and a Transmission snapshot that `statx`es every file of
  every torrent.
- `EvaluateAllAsync` also runs synchronously in the Keep request (`EntriesController.cs:249`) and
  on every configuration or user update.

The revalidation is valuable, but running the whole library each time costs minutes on a Pi and
writes to storage constantly. **Fix:** revalidate only the affected target(s) and path group
right before unlinking. Only write an evaluation when its state or deadline changes. Reuse one
Transmission snapshot per batch, re-querying just the affected torrent before unlinking.

### 3.2 Medium

| ID | Finding | Evidence | Status |
| --- | --- | --- | --- |
| M1 | **Deleting an entry races retention and cascades away the audit trail.** `Remove` takes no library lock or retention gate. `RetentionOperation` → `Entry` is `Cascade`. | M2 | **A stale binding hides an entry from everyone, including admins.** `CanRead` requires the bound native item to be enumerable. If the native ID changed and the event was missed, List/Detail/Keep/Remove/Refresh all return 404 until reconciliation runs. | `LibraryAccess.cs:47–48` | Confirmed |
| M3 | **Duplicate-add monitoring depends on timing.** An add that finds the entry before the lock returns it unchanged. An add that loses the race goes through `CompleteConcurrentAdd`, which sets the entry and **all episodes** to monitored, overriding admin per-episode choices. | M4 | **Strict TMDB season check may reject airing series.** Add/Refresh fails with 502 if a season endpoint's episode count differs from the series' `episode_count`; these often disagree briefly for airing seasons. | M5 | **Search parity regression.** The combined Movies/Shows search sections replace stock ones and match `Title.Contains(query)` only. | M7 | **Storage identity may change on reboot.** The mount identity includes device `major:minor`, and the physical identity is `dev:inode`. FUSE (mergerfs), NFS and overlay filesystems get new anonymous device numbers across reboots, and mergerfs inodes are not always stable. That leaves everything `storage_unavailable` / `media_identity_changed` until a full reconciliation. Safe, but it can stall retention silently. | `MediaStorageIdentity.cs:102`, `UnixFileInspector` | Plausible — check the Pi filesystem |
| M8 | **Playback progress causes writes and refetches.** Every `UserDataSaved`, including playback progress every few seconds, queues a completion refresh and evaluation that writes SQLite. Every web `UserDataChanged` also invalidates Browse/Home/Search queries. | M9 | **Keep is one-way.** Nothing reverts `never` → `inherit`. The T5 button just shows a pressed "Kept" state. An accidental Keep, or a Keep made "for now", is permanent unless someone edits the DB. | `EntriesController` Keep, `EntryDetails.tsx`, `NativeEntryDetails.tsx` | Confirmed |
| M10 | **Manual retention run is tied to the HTTP request.** `POST /Retention/Run` runs the batch inside the request with the request's cancellation token. ### 3.3 Low and hygiene

- `LibraryAccess.GetLibraries` maps every non-`"movie"` type to `tvshows` (`:30`). Callers
  validate today, but a future caller passing `"episode"` would silently get TV libraries.
  Throw instead.
- `CanReadMetadata` hides unrated file-less titles from **any** user with a max parental rating
  (`:63`). It also hides **all** discovery and file-less titles from users with AllowedTags
  (`:58`). Both are intentional and conservative, but users get no explanation. Document them
  in UX §14 and show a message.
- Browse `limit` allows up to `int.MaxValue`, and null means unpaged, hydrating DTOs for the
  whole library. Consider a server cap.
- Search's admin **Undo** toast is a `<button>` appended to `body` for 4 seconds. It is not
  reachable by D-pad, so Undo effectively doesn't exist on TV.
- `fetchLegacyBrowse` catches every error and silently uses native `getItems`. That is right
  for degradation, but it also hides 400 contract drift in TV layout. Log unexpected status codes.
- After reclaim, sidecars (NFO, subtitles, trickplay, extras/trailers) and empty folders stay.
  This is intended (T3), but extras are real disk use and folders accumulate. Plan a cleanup
  policy.
- A fixed 25-path daily batch means enabling retention on a large watched TV backlog takes weeks.
  Make it configurable, and show "N due, M processed per day" in preview.
- `API.md` is missing `POST /Entries/{id}/Refresh`, `GET /Reconciliation/Latest`, Browse
  `dueWithinDays`, and the `retention` field on Browse rows.
- TMDB token and Transmission password are sent in clear to the admin Dashboard config page.
  This is the standard Jellyfin pattern, but it conflicts with PHASE4's "secret reads return
  presence indicators". Decide once for all secrets.

## 4. What is solid

These are worth keeping as the project grows:

- Server-derived identity (`Jellyfin-UserId` claim). 404 concealment. Admin writes behind
  `RequiresElevation`. Content/parental checks for file-less titles.
- `(mediaType, tmdbId, targetLibraryId)` identity with a unique index. Catching the insert race
  (`SqliteErrorCode 19`) and returning the canonical row.
- Retention execution: a durable operation before unlink, revalidation under library locks,
  device/inode and mount identity, symlink and escape rejection, exactly-once `reclaimed` history,
  and honest logical vs physical byte accounting.
- Fail-closed defaults: unknown seed state, unknown sessions, missing storage and missing
  evaluation all block.
- Graceful degradation in the web client. Query keys include server and user. `placeholderData`
  guards stop one user's grid from leaking to another.
- Acceptance evidence recorded against a real host, with production kept out of it.

### 5.3 Phase 4 (indexers and manual grab)

The draft is careful, but it is too large for one phase and has one factual conflict:

1. **Pick the download client from the deployed environment.** Phase 3 found and integrated
   Transmission; Phase 4 plans qBittorrent. Either write the Transmission driver (`torrent-add` is
   simple), or add a qBittorrent **read** adapter to retention in the same phase. Otherwise
   Phase 4 torrents get no seed protection.
2. **Split it into shipping slices:**
   - **4a:** movies only, admin-only, one Torznab source (Prowlarr gives many indexers through
     one endpoint), a fixed built-in profile.
   - **4b:** episodes and profiles.
   - **4c:** rejection explanations and multiple indexers.

   The A1–A8 evidence list can apply to each slice.
3. **Add a hard seed-requirement model now** (H4): minimum ratio and seed time per indexer,
   snapshotted on the grab, and enforced by retention whatever client goals say.
4. Take the Phase 5 reclaim ownership decision (H3) **before** designing the grab record, so the
   torrent ID/hash is stored in a form retention can later use to remove the client copy.
5. **Worth reconsidering:** an "acquisition backend" interface with a **Radarr/Sonarr adapter**
   next to the native engine. README §1 already puts the engine behind an interface. Delegating
   to an existing *arr through its HTTP API (no GPL code copied) would deliver end-to-end
   acquisition in weeks. The native engine could then replace it gradually, if it is still wanted.

### 5.4 Phases 5–6

- Phase 5 needs **path mapping** between the client container, the Jellyfin container and the
  library (the same issue as H4), and a same-filesystem check at configuration time.
- Retention and multiple versions (Phase 6): define whether retention reclaims **lower-quality
  versions first** once a better one is watched, not just whole titles.
- Upgrade-to-cutoff replaces files, which will look like "external removal" to Phase 2. Reuse the
  retention operation provenance pattern so upgrades don't emit `media_missing`.

## 6. Ideas

**Safety and trust (retention deletes things):**
- **Soft delete / quarantine:** instead of `File.Delete`, rename into a hidden
  `.jellyfinmod-trash/` on the same filesystem (atomic, no copy) and purge after N days. That
  makes the unrecoverable step reversible, and the T3 operation model already fits it.
- **Advance notice:** a daily "expiring in 72h" digest through a Jellyfin notification, a
  webhook, or a Home row for admins. This is not a per-item confirmation, so it stays consistent
  with the accepted decision.
- An **admin Retention page** in the Dashboard that renders `/Retention/Preview`: counts by
  reason, "waiting on N users" (counts only, no names shown to non-admins), and the next run
  estimate. The JSON API exists; admins currently have no view of it.
- **Rethink the All users default** for real households: one user who never watches blocks
  every title. Consider "active users (played anything in the last N days)" as a fourth mode, or
  show in preview how many items All users is holding back.

**Catalog and discovery:**
- A TMDB metadata cache table with TTL. Use the server's preferred metadata language instead of
  `en-US`. Optionally proxy and cache TMDB posters so TVs don't fetch `image.tmdb.org` directly
  (privacy, offline and slow networks).
- Import watchlists from Trakt, Letterboxd or IMDb lists (the README already names Trakt).
- "Requested by" attribution on shared entries, and a per-user "My wants" filter.
- An **Upcoming** Home row for monitored series with air dates, and a "now available"
  notification when Phase 2 binds a wanted title.

**Operations:**
- Extend `/JellyfinMod/Health` with components: DB migrations, TMDB configured/reachable,
  seed client reachable, last reconciliation and retention runs.
- Automatic SQLite backup before each migration (backups are manual today), with retention of
  the last N.
- A reproducible **large synthetic library** fixture on the test instance for performance gates
  (H5/H6).

## 7. Recommended order of work

1. Fix **H1** (evidence bootstrap) and **H2** (Refresh) with integration regressions. Both are
   small and affect correctness.
2. Commit or push the pending work. Resolve the uncommitted playback-file changes in the main
   `jellyfin-web` checkout. Make one docs copy authoritative.
3. Fix **M1** (delete versus retention) and **M9** (un-Keep). Then run **T5 acceptance and T6**
   on the isolated instance, with the Transmission paths checked for H4.
4. Measure **H5/H6** on the Pi with a synthetic large library. Fix the access-check and preview
   hot paths before the catalog grows.
5. Before Phase 4 starts: decide the client (Transmission or qBittorrent), the seed floor model
   (H4) and who owns reclaiming the seeding copy (H3). Split Phase 4 into slices, and decide
   whether an *arr adapter comes first.
6. Consider quarantine-based deletion before turning retention on for real media.
